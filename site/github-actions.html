Only run code you control

Vendored GitHub Actions

In October 2020 I brought three community GitHub Actions into my own GitHub account and reviewed them, so my pipelines only run code I have read. Each one started life as an open-source community action, and the README of each copy gives the reason it moved: only run code you control and have gone over. It was an early supply-chain hygiene habit: a third-party action runs with your repository's secrets, so pointing your workflows at a copy you own and have read is cheap insurance against a tag being moved or an upstream being compromised.

actions-docker-publish

github.com/liskl/actions-docker-publish

Builds a Docker image and pushes it, using the git branch as the image tag; the default branch publishes as latest. It works with Docker Hub, GitHub Packages, GitHub Container Registry or any custom registry through the registry input.

  • snapshot pushes an extra tag built from a timestamp and the short git sha
  • tag_names and tag_semver tag images from git tags, with tag_semver turning v1.2.3 into 1.2.3, 1.2 and 1
  • cache, buildargs and buildoptions tune the build
  • dockerfile, workdir and context pick what gets built and from where
  • Outputs: tag, snapshot-tag and digest

Testing: bats unit tests run during the image build, with a mock shim standing in for docker and date. Separate integration workflows publish to a custom registry and to GitHub's package registry, a bump_version workflow tags releases, and a Renovate config is checked in for dependency updates.

- name: Publish to Registry
  uses: liskl/actions-docker-publish@main
  with:
    name: myorg/myimage
    username: ${{ secrets.DOCKER_USERNAME }}
    password: ${{ secrets.DOCKER_PASSWORD }}
    snapshot: true

actions-github-tag

github.com/liskl/actions-github-tag

Bumps and tags the release branch with the next SemVer version on merge. Commit messages can ask for a #major, #minor or #patch bump; otherwise it falls back to DEFAULT_BUMP (minor unless set). Other options include WITH_V for a v prefix, RELEASE_BRANCHES for which branches cut release tags (main by default), and DRY_RUN to compute the next version without tagging. Any other branch gets a version suffixed with the short commit sha and no tag is pushed.

actions-k8s-deployer

github.com/liskl/actions-k8s-deployer

Decodes a base64 KUBE_CONFIG_DATA secret into a kubeconfig and runs whatever kubectl command you pass it, which covers both the deploy and the check that it worked.

- name: Deploy
  uses: liskl/actions-k8s-deployer@main
  env:
    KUBE_CONFIG_DATA: ${{ secrets.KUBE_CONFIG_DATA }}
  with:
    args: set image deployment/app app=registry.example.com/app:${{ github.sha }}

- name: Verify rollout
  uses: liskl/actions-k8s-deployer@main
  env:
    KUBE_CONFIG_DATA: ${{ secrets.KUBE_CONFIG_DATA }}
  with:
    args: rollout status deployment/app

Then and now

The same three jobs (tag, publish, deploy) still run this site, with the deploy step now pulled rather than pushed. Every merge to master is a release: conventional-commit tagging pushes a vX.Y.Z tag, CI builds the nginx image and pushes it to GitHub Container Registry, and Flux image automation picks up the new tag and rolls it out on the homelab cluster.
